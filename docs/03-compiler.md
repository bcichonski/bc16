# bc: compiler for the B language

`src/bc/` compiles **B**, a small C-like language, into bc81asmc assembly (`.basm`) for the
bc8183 CPU. The current version is **v1.3.1 (240927)**. It is written in Python with
[parsy](https://pypi.org/project/parsy/). bdos, all of its utilities and the user apps are
written in B.

| File | Contents |
|---|---|
| `bc.py` | CLI, preprocessor, top-level compile step |
| `bc_grammar.py` | parsy grammar for expressions, statements and functions |
| `bc_ast.py` | AST node classes, each with `emit()`: scopes, variables, code generation, constant-operand optimisations |
| `bc_stdlib.py` | assembly runtime library appended to every program |
| `bc_dbg.py`, `tests/bc_tests.py` | debug helper, unit tests |
| `grammar.txt`, `history.txt`, `bugs.txt` | design notes, code-size optimisation history, known bugs |
| `code_size.csv` | committed code-size log per program (date, program, start, bytes, `.basm` hash), reported by `scripts/code_size.py` |
| `code/` | small test programs (`declarations.b`, `functions.b`, `funrec.b`, `stdmemtest.b`, …) |

## Usage

From `src/`:

```bash
./bcc bdos/helloworld          # compile helloworld.b -> .basm, then assemble -> .btap
bcc bdos/helloworld            # the same console command (after `pip install -e .`), any directory;
                               # the path is given without .b, relative to the current directory
```

That is the same as running:

```bash
python bc/bc.py bdos/helloworld.b                 # -> bdos/helloworld.basm
python bc81asmc/bc81asmc.py bdos/helloworld.basm  # -> bdos/helloworld.btap
```

- Without flags the compiler prints one line, `bc: <name>.b -> <name>.basm`, and exits 0. Nothing
  else is printed on a successful compile.
- `--verbose` prints the compiler's trace (scope and variable echoes, progress lines) and also writes
  the preprocessed source to `<name>.genb`. `bcc` does not pass `--verbose`, so it writes no `.genb`;
  run `bc.py --verbose` directly to get one. `--btap` is obsolete.
- Every `.basm` the compiler writes starts with the line `; generated by bc from <name>.b - do not edit`
  (the source file name). It is an assembler comment, so the `.btap` is the same without it.
- Errors and warnings go to stderr as `<file>: error: <message>`, or `<file>:<line>:<col>: error: <message>`
  once a location is known, and the compiler exits with code 1 without writing a `.basm`. A parse error
  gives the 1-based line and column in the preprocessed source (not the original file, until #28), the
  line itself with a `^` caret, and parsy's `expected …` text. `--verbose` adds the numbered lines around
  the failure and the traceback.
  An internal compiler fault (for example, an operator the grammar accepts but code generation can't
  emit) is reported as `internal error: <message>` and also exits with code 1 without writing a `.basm`,
  for example `internal error: Unknown binary operator '<op>'`.
  An undeclared variable is reported as `Undeclared variable <name>` (no location until #28) and stops the
  compile: it exits with code 1 without writing a `.basm`.
- Python dependency: `parsy`, the only one. The compiler runs on Python >= 3.10 on Linux,
  macOS and Windows (CI tests 3.14). Output files are written as UTF-8.

## Preprocessor

The preprocessor works line by line, before parsing:

| Directive | Effect |
|---|---|
| `#include file.b` | paste the file in (path relative to the **main** source file's directory) |
| `#define NAME value` | token replacement. `NAME` is the first token, `value` is the rest of the line. Whole identifier tokens equal to `NAME` are replaced in code and in the string directly after `asm`; other strings, char literals and `//` comments are untouched. A redefinition with a different value warns and the last value wins; a malformed define is an error |
| `#link NAME` | records `NAME` (one B identifier) as an object the program needs. No effect without `--obj`: the output is the same and the line is dropped. Names are kept per compile, in order, duplicates once. A malformed line is an error: `malformed #link (expected: #link NAME): <line>`. Writing them into the object as a `de` record is #121 |
| `#code 0xHHHH` | address of the code (`.org`). Default `0x1000`; bdos programs use `0x6000` |
| `#heap 0xHHHH` | start of the heap used by `malloc`. Default `0x3000` |
| `#codelimit 0xHHHH` | optional second limit: the program's image must end below this address. Reset for every compile, so it has no default. `bdos.b` uses `0x5d00` |
| `// …` | a line starting with `//` is dropped |

A `#define` value is not rescanned, and numbers are scanned whole, so `0x10` is never matched by a define named `x10`. `MAXLINE` is not matched by a define named `MAX`.

## Language

### Types

| Type | Meaning |
|---|---|
| `word` | 16-bit unsigned |
| `byte` | 8-bit unsigned |

Every expression is evaluated as 16 bits. The type only decides how many bytes a variable
takes; assigning to a `byte` stores the low byte. Types aren't checked otherwise.

### Literals

- decimal `123`, hex `0x1f`, `0xABCD`, character `'A'`
- `"string"`: there are no escapes. The string goes into the data segment with a `0x00`
  terminator, and the expression evaluates to its address.
- There are no negative literals and no unary minus.

### Operators

From tightest to loosest binding. Operators on the same level evaluate left to right.

| Level | Operators | Notes |
|---|---|---|
| 1 | `#e`, `!e`, `~e` | `#` reads the 16-bit big-endian word at address e; `!` is logical not (result 0/1); `~` is bitwise not. **A unary operator applies to the whole rest of the expression**, so `!a = b` means `!(a = b)` |
| 2 | `*` `/` `%` | 16-bit hardware mul/div/mod |
| 3 | `+` `-` | |
| 4 | `&` `\|` | bitwise |
| 5 | `<<` `>>` | |
| 6 | `&&` `\|\|` | `&&` gives 0/1; `\|\|` is a bitwise OR (truthy, not normalised to 1) |
| 7 | `<` `<=` `>` `>=` | unsigned, result 0/1 |
| 8 | `=` `!=` | `=` is **equality**, result 0/1 |

> The precedence is unusual: comparisons bind *looser* than `&&`/`||`, and shifts bind
> looser than `&`/`|`. Write `(a > 0) && (b = 1)` with parentheses; that's what the bdos
> sources do.

Function calls are written `name(arg, arg, …)`. The argument list can span several lines.

### Statements

| Statement | Syntax |
|---|---|
| variable declaration | `word name;` / `byte name;` |
| assignment | `name <- expression;` |
| expression | `expression;`: a call, or a bare variable to load its value into `csci` for the next `asm` |
| if / else | `if (e) { … } else { … }`. `else` may be followed by a single statement, so `else if (…) {…}` works |
| while | `while (e) { … }` |
| return | `return expression;` |
| inline asm | `asm "mov a, #csci";`: the text is copied verbatim into the output |
| raw-byte asm | `asm item, item, …;`: one `.db` line of bytes and label references, see [Raw-byte asm](#raw-byte-asm) |
| comment | `// …` |

There is no `for`, `break`, `continue`, arrays, structs or pointer types. Memory is accessed
through `#addr` and the `peek8/peek16/poke8/poke16` library functions.

### Raw-byte asm

`asm item, item, …;` puts raw bytes in the output, for code the compiler cannot write yet. The design is in
[07 "Raw `asm` in B"](analysis/07-self-hosted-compiler.md#raw-asm-in-b). The statement is not `asm "…"`: a string
after `asm` keeps its old meaning until #127.

| Item | Bytes | Output |
|---|---|---|
| decimal or `0x` number 0–255, or a `#define` name whose value is one | 1 | `0xHH` |
| `:name` (a label) | 2, high byte first | `:name` |
| `hi(:name)` / `lo(:name)` | 1 | the same text |

```
asm 0xd8, 0x81;                       // -> .db 0xd8, 0x81
asm 0xd8, :poke16, hi(:x), lo(:x);    // -> .db 0xd8, :poke16, hi(:x), lo(:x)
```

- The statement writes one `.db` line where it stands, with no other code around it. `bc81asmc` assembles it
  like any `.db`. The assembler accepts `hi(:name)` and `lo(:name)` as `.db` operands (decision A12, see
  [02-assembler.md](02-assembler.md)).
- `#define` names are replaced in items like anywhere in code (C5). A define named like a label used as `:name`
  replaces that label too.
- Char literals are not items: `'a'` is an error.
- Labels in items count for the dead-code step, so a function referenced only from `:name` or `hi(:name)` is kept.
- Every bad item is reported, and the compiler exits with code 1 without writing a `.basm`:

  ```
  file.b: error: raw asm: 256 is out of range (0-255)
  file.b: error: raw asm: unknown item 'foo' (expected a number 0-255, :name, hi(:name) or lo(:name))
  ```

### Functions

```c
byte add(word a, word b)        // definition
{
    return a + b;
}

byte later(word x);             // forward declaration (no body)

byte printf(word PformatStr)*** // variadic: extra args become word params P1, P2, …
{ … }                           // and "<name>PLEN" holds the argument count
```

- The program must define `main`. It is called from the generated entry point, and the
  program ends with `ret` (so it returns to bcOS `r` or to the bdos shell).
- A function's return value is whatever is in `csci` when it returns: the value of
  `return e`, or the last evaluated expression. `peek8` and similar functions rely on this.
- `return` may appear anywhere in a function, including inside nested `if`/`else` and `while`.
  It emits `ret` at that point, which is safe because the caller owns the frame: the caller
  moves `sys_stackhead` forward before `cal` and back after it returns, and the callee never
  moves it. Blocks open no scope (C2, C8), so an early `ret` skips no unwinding code.
  A function whose last statement is `return` ends with a single `ret`.
- Blocks don't open a new scope: all locals of a function share one scope, so names must be
  unique within a function.
- Recursion works, because every call gets its own frame (see `code/funrec.b`).
- Top-level `word x;` / `byte x;` declarations are accepted as globals, stored in the base
  frame.
- Assembly labels are `F<NAME up to 10 chars><id>`. Data labels are `DATAxxxx` and jump
  labels `LABELxxxx`. Since #104, a jump or function label is written alone on its own line,
  with no `nop`, so it costs no bytes. Label-only lines need the assembler support added by
  #103. Hand-written `asm "label:"` lines in the B libraries (`stdio.b`) follow the same rule.

## How the generated code works

- **Registers:** an expression's result is left in `csci`, and the right-hand operand of a
  binary operator in `dsdi`. Intermediate values are pushed on the CPU stack. If the right
  operand of a commutative operator is a constant, it is loaded straight into `dsdi`, which
  skips a push/pop. Comparisons with constant `0` are shortened.
- **Variables:** variables don't live on the CPU stack. They live in a separate **software
  stack** whose pointer is `sys_stackhead`, placed just after the program image and growing
  upwards. A call moves `sys_stackhead` forward by the caller's frame size, stores the
  arguments as the callee's first locals, `cal`s the function, then moves it back. Variables
  are read and written relative to `sys_stackhead` through runtime helpers
  (`stackvar8gt8/16`, `stackvar8st8/16` for offsets up to 127, `stackvarget/set8/16` for
  larger ones). The CPU stack (from the top of memory downwards) holds only return addresses
  and temporaries.
- **Heap:** `sys_heaphead` is set to the `#heap` address at start-up. `stdmem.b`
  implements `malloc`/`mfree` on top of it.
- **Program layout:** the output is laid out in this order: `.org #code`, the entry point
  (init stackhead and heaphead, `cal main`, `ret`), the kept functions, the data segment
  (kept strings), the kept runtime fragments, `sys_heaphead`, then `sys_stackhead`, then the `sys_codeend` label.
- **Labels:** a label costs no bytes. The host writes `LABELxxxx:` and `F<name><id>:` on
  their own line, with no `nop`. The `nop` that remains in the runtime, `sys_stackhead: nop`,
  is not a label: its byte is the low byte of the software-stack pointer word, so it stays.
- **Build-time checks:** the last line is `sys_codeend: .assert :sys_codeend < 0x<heap>`, so the
  assembler fails the build if the image reaches the `#heap` address. The label costs no bytes.
  With `#codelimit 0xHHHH`, a second line `.assert :sys_codeend < 0xHHHH` checks the same label
  against that limit. A failure is reported as `assertion failed` (see [02-assembler.md](02-assembler.md)).

### Dead-code elimination

- **Rule:** every function is compiled first, so errors are still reported and label numbers are
  unchanged. Then only the function chunks reachable from the entry point are kept, in source order.
  A chunk is a function's code (from `;FUNCTION` to `;END OF FUNCTION`) plus the string literals
  created while emitting it. A chunk is reachable when kept text contains a `:label` reference to a
  label it defines.
- **References:** every `:name` outside `;` comments counts (`cal :F…`, `clr`/`jmp`, `.mv rr, :label`,
  `.assert`). Labels in raw-byte `asm` items (`:name`, `hi(:name)`, `lo(:name)`) count the same way.
  Labels defined inside `asm` strings count too: `bdos.b`'s `main` loads `:bdio_call`,
  a label in an `asm` string of `bdio.b`'s `bdio_call()`, so that function is kept. Comments do not count.
- **Runtime:** `bc_stdlib.py` is a list of fragments, one per routine, each with a declared list of
  the fragments it depends on. A fragment is emitted when kept code references one of its labels,
  plus the closure of its declared dependencies, in template order. A unit test checks that each
  declaration equals the labels the fragment's text references.
- **Always kept:** the entry code, the runtime banner and head lines, `sys_heaphead`, `sys_stackhead`
  (it stays the last byte of the image), `sys_codeend` and its asserts. `sys_stdprntf` and `sys_seektmp`
  are kept only when used (`printf`, `mseek`).
- **Output order:** `.org`, the entry point, the kept functions, the kept strings, the runtime banner,
  the kept runtime fragments in template order, the runtime data. Every distance between two kept labels
  can only shrink, so no relative jump goes out of range.
- **Sections:** each runtime fragment is meant to become one `.sect` of `runtime.basm` (#116),
  linked by blink (#126).

### Runtime stdlib (`bc_stdlib.py`, assembly)

Each routine is a fragment of `bc_stdlib.py` with its declared dependencies. A routine is emitted only
when the kept code uses it, directly or through another routine. The table lists every routine the runtime can emit.

| Group | Routines |
|---|---|
| OS bridge | `os_metacall`-based calls into bcOS (see [04-bcos.md](04-bcos.md)); `src/bc/tests/bc_runtime_bcos_tests.py` checks the runtime's `.def` addresses and metacall indices against `bcos.basm` |
| Printing / errors | `fatal`, `printhex4/8/16`, `print_newline`, `printstr` |
| Memory | `poke16`, `peek16`, `mfill`, `mem_cpy`, `mseek` |
| Strings and parsing | `readstr`, `nextword`, `nextval8`, `upchar`, `str_cpy`, `str_len8`, `strncpy`, `parsehex4/8/16` |
| Comparisons | `gt16`, `gteq16`, `eq16` |
| Variable stack | `stackoffscalc`, `stackoffsclc8`, `stackheadroll`, `stackheadrll8`, `stackvarget8/16`, `stackvarset8/16`, `stackvar8gt8/16`, `stackvar8st8/16` |
| Runtime data | `sys_stdprntf`, `sys_seektmp`, `sys_heaphead`, `sys_stackhead` |

## Example

```c
#code 0x6000
#heap 0xf000

#include std.b
#include stdio.b

byte main()
{
    putsnl("Hello world!");

    word a;
    a <- 10;

    putdecwnl(a);
}
```

## Code-size history

From `bc/history.txt`:
- dedicated stack-head subroutines cut code size by 38% (v0.6);
- in v1.2.0, commutative-operand and constant-loading optimisations shrank bdos from 14339
  to 13063 bytes;
- the bc8183 port replaced library calls for `+ - * / %` and the bitwise operators with
  native 16-bit instructions;
- #16: unused functions, strings and runtime routines are no longer emitted; total code went from
  105367 to 77385 bytes (-27982).

Current sizes are in `src/bc/code_size.csv` (append-only; the latest row per program wins).
`python3 scripts/code_size.py` prints them; `--check` (optional, local) exits 1 when a program's code differs from its
latest row. Metrics only: nothing fails CI or the unit suite on a size change. After an intended
codegen change, running `python3 scripts/code_size.py --record` and committing the appended rows with the change is recommended.
The CI unit job on Python 3.14 adds the table to the job summary.
