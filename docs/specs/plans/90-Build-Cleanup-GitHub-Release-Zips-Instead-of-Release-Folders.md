## 1. Problem Statement

*   **Context**: the repo mixes sources, build intermediates and two frozen release snapshots (`release/bc16_v1.0`, `release/bc32_v1.0`, 68 files). The snapshots aren't runnable (their `run` scripts load a `../rom/*.b81` that was never committed). `.gitignore` lists generated files one by one, yet 37 of them are tracked anyway (`git ls-files -i -c --exclude-standard`). Compiler output (`.basm` next to its `.b`) is committed and churns every PR that touches the compiler. Stale files exist (`src/bdos.bdd`, `src/bc/code/strings.btap`, `bcos_v1_1_0.b81`, `bcos_v1_1_1.b81`). Tests sit next to the code (`src/bc64/test_*.py`, `src/bc/*_tests.py`, `src/bc81asmc/*_tests.py`, `src/test_*.py`).
*   **Goal**:
    1. Old generations ship as GitHub Release zips anchored on tags, and `release/` leaves `bc64`. A `release.yml` workflow builds the bc64 zip from a `bc64-v*` tag.
    2. Only what's needed to **run** (current ROM, shipped discs, test fixtures) and hand-written sources are committed. Every derived file is ignored and untracked, and CI guards it.
    3. Generated `.basm` files carry a "generated by bc" header.
    4. Each tool's tests move into a `tests/` folder of that tool (owner comment).
*   **In scope**: everything in the issue's Proposal and AC, plus the owner's test relocation.
*   **Out of scope**: the issue's "Out of scope" list (`bc/grammar.txt`, `rundebug`, a `build/` folder). **Publishing**, meaning pushing tags and creating the GitHub Releases, is done by the owner after review (D1). No byte-for-byte "rebuild equals committed" test is added.

### 1.1 Technical Summary

*   **Touched areas**: `.gitignore`, the index (untracking), `src/bc/bc.py`, `run_tests.py`, `.github/workflows/tests.yml`, a new `.github/workflows/release.yml`, a new `scripts/make_release.py` (+ `scripts/tests/`), every test module (moved), and the docs (README, CLAUDE.md files, `docs/01`, `04`, `05`, G9).
*   **New patterns**: release zips built by one stdlib-only script, used by CI and by the owner; per-tool `tests/` packages run by `run_tests.py`.
*   **Infrastructure changes**: CI builds the ignored intermediates before the e2e tests, and guards tracked/ignored consistency and `.basm` placement. Tag-triggered release workflow.
*   **End state**: a fresh clone runs `./run` with `os.bdd` immediately. The full pipeline (`./buildos && ./buildtools && ./buildapps && ./makedisc`) recreates every ignored file it needs without changing a tracked file. `release/` is gone. The owner publishes `bc16-v1.0`/`bc32-v1.0` with one documented command per release.

### 2.4 Key Behaviour

*   **Commit rule:** a `.basm` with a `.b` of the same name in the same folder is a build output. Commit what's needed to run (ROM `bcos_v1_2_0.b81`, `os.bdd`, later `utils.bdd`), the test fixtures (`src/bc64/testdata/*.bdd`) and hand-written sources (`bcos.basm`, `boot.basm`, `examples/*.basm`, `testb.sectors` as sample data).
*   **Generated header:** every `.basm` that `bc.py` writes starts with `; generated by bc from <X>.b - do not edit` (basename of the source). It adds no bytes to the `.btap`.
*   **Release zips** (`scripts/make_release.py`, stdlib only, Python ≥3.10, run from anywhere in a full clone):
    *   `bc64 --tag <name> [--out DIR]`: a zip `<name>.zip` with one root folder `<name>/`. It holds the tracked files (from `git ls-files`, so ignored outputs never leak in) of the emulator (`src/bc64.py`, `src/bc64/`), the ROM, `src/os.bdd` (+ `src/utils.bdd` once it exists), the toolchain (`src/bc/`, `src/bc81asmc/`, `src/bdos/`, `ftool*.py`, `bc64_toolchain.py`, `disc.bddmanifest`, the bash scripts), `README.md`, `LICENSE`, `pyproject.toml` and `docs/0*-*.md` + `docs/README.md`. It excludes every `tests/` folder, `testdata/`, `docs/specs/`, `docs/analysis/`, `docs/CHANGELOG.md` and `.github/`. Unix modes are kept (scripts stay executable). From the unpacked zip, `cd <name>/src && ./run` starts the machine.
    *   `legacy bc16|bc32 [--out DIR]`: zip `<gen>-v1.0.zip`, root `<gen>-v1.0/`, holding `release/<gen>_v1.0/` as at `7d4cda9`, plus `rom/` (bc32: `src/bc81asmc/bcOS/bcos_v1_1_1.b81` at `6304761`, the release commit, F13; bc16: `bcos.b81` assembled from `bd2498a`'s `src/bc81asmc/bcOS/bcos.basm` with `bd2498a`'s assembler, F5), plus the `run` script with `winpty python` replaced by the interpreter pick of `src/run` (the one allowed change, D2), plus a short `RELEASE-NOTES.md`. Source commits are constants in the script, read via `git archive`/`git show`, so the command works after `release/` is deleted.
    *   `notes bc64|bc16|bc32`: prints the release notes, i.e. the README's `# BC64` / `# BC32` / `# BC16` section. Legacy notes also mention the `run` interpreter change and the ROM origin.
*   **`release.yml`**: on push of a `bc64-v*` tag it installs (`pip install -e .`), builds the intermediates, restores the committed ROM/os.bdd, runs `run_tests.py`, builds the zip and creates the GitHub Release with it (`gh release create`, `contents: write` on that job only, notes from `notes bc64`). On `workflow_dispatch` (input: zip name, default `bc64-dryrun`) it does everything except publishing, and uploads the zip as a workflow artifact.
*   **CI build step (tests.yml, e2e job, before the smoke refresh):** `cd src && ./buildos && ./buildtools && ./buildapps && ./makedisc`, then `git checkout -- src/os.bdd src/bc81asmc/bcOS/bcos_v1_2_0.b81`, then fail if `git status --porcelain` is not empty (a build that touches a tracked file means an output isn't ignored). The committed disc/ROM are restored, never compared (D8).
*   **CI guards (tests.yml, unit job, beside the cpudebug.log guard):** fail if `git ls-files -i -c --exclude-standard` prints anything, and fail if a tracked `X.basm` sits beside a tracked `X.b` in the same directory. The "release/ untouched" guard is removed from both jobs.
*   **`run_tests.py` hint:** when the e2e suite is selected and any `SOURCE` file named in `src/disc.bddmanifest` is missing, the e2e suite is reported FAIL with one line naming the first missing file and the pipeline command (`cd src && ./buildos && ./buildtools && ./buildapps && ./makedisc`), without running it. Other suites run as usual.
*   **Test layout (D10):**

    | Tests of | New folder | Run as (cwd) |
    |---|---|---|
    | emulator package + `bc64.py` CLI | `src/bc64/tests/` (`bc64/test_*.py`, `test_bc64_cli.py`) | emulator suite (`src`) |
    | assembler | `src/bc81asmc/tests/` (all `*_tests.py`) | assembler suite (`src/bc81asmc`) |
    | compiler | `src/bc/tests/` (all `*_tests.py`) | compiler suite (`src/bc`) |
    | tools living directly in `src/` (ftool, toolchain launcher, run_tests), the system e2e tests and their harness | `src/tests/` (`test_ftool.py`, `test_bc64_toolchain.py`, `test_run_tests.py`, `test_e2e_*.py`, `test_bc64_smoke.py`, `e2e_harness.py`) | ftool / emulator / e2e suites as today (`src`) |
    | release script | `scripts/tests/` | new `release` suite (unit group) |

    Suite membership and per-suite test counts stay as today (only the release suite is new). Test data stays where it is (`src/bc64/testdata/`, `src/bc/…`). File names keep their pattern.

## 3. Key Decisions & Assumptions

*   **D1. Publishing is the owner's step.** The issue says "This publishes something, so the owner approves it first", and the sandbox safety rule forbids outward changes without approval. The run does not push tags, create releases or dispatch workflows. It ships the tooling, builds and boot-checks all three zips locally, and documents in README ("Releases") the exact owner commands: `git tag bc16-v1.0 bd2498a`, `git tag bc32-v1.0 6304761`, push the tags, and `gh release create <tag> dist/<tag>.zip --title … --notes-file …` built with `make_release.py`. AC-1's "releases exist" is completed by the owner; the PR description says so.
*   **D2. Legacy zip content** is `release/<gen>_v1.0/` as at `7d4cda9` (F4) plus `rom/`. The bc32 ROM comes from the release commit `6304761`, because the later copy no longer boots bc32 (F13, A1). The only change to frozen content is the `run` interpreter pick, as the issue allows. Tags point where the issue says (`bd2498a`, `6304761`) even though the bc16 zip content is newer than its tag commit (later tapes). The issue asks to zip the folders "as they are", and the release notes mention it.
*   **D3. bc16 ROM** is rebuilt at release time by the script from `bd2498a` (F5), not committed anywhere. It's checked by booting `hello.run.btap` from tape on a pty (T6).
*   **D4. Release tooling** lives in `scripts/make_release.py` (Python, stdlib only), with tests in `scripts/tests/`, run by `run_tests.py` as unit suite `release`. It's repo tooling, not a machine tool, so it stays out of `src/`.
*   **D5. Zip names and roots:** `<tag>.zip` → `<tag>/…`; `dist/` (already gitignored) is the default output folder.
*   **D6. `.gitignore`** gets the issue's block verbatim (comments on their own lines), replacing the bc-specific lines. `*.bin` and the generic Python/IDE sections stay.
*   **D7. `src/bdos/testb.sectors` keeps its name** (the issue only says "consider" moving it). The `!` exception keeps it tracked.
*   **D8. CI rebuilds the ignored intermediates but never compares rebuilt committed outputs**: the ROM and os.bdd are restored with `git checkout` after the build (the issue and the owner rule out a rebuild-equals-committed test). The existing e2e checks that read intermediates (`test_e2e_disc` structure vs the manifest, `test_e2e_theodore` sector count) keep their meaning: the committed disc must match the sources' builds.
*   **D9. No auto-build in `run_tests.py`**: building rewrites the tracked ROM/os.bdd, so the runner only names what's missing and the command (§2.4).
*   **D10. Test layout** as in §2.4 (owner comment). "The tool's folder" for tools that live directly in `src/` (ftool, launcher, run_tests runner, the whole-system e2e tests) is `src/`, so their tests go to `src/tests/`. That isn't a shared folder for component tests: each component's tests are in that component. `test_bc64_smoke.py` boots the whole system and belongs to the e2e suite, so it goes to `src/tests/` with the e2e tests. Test files keep their names and suite membership. Moving changes only imports and path computations, never assertions.
*   **D11. Ignored files the pipeline doesn't build** (`debug`, `fddtest`, `src/bc/code/*`) are rebuilt on demand with `./bcc`; README/`docs/05-bdos.md` say so. AC-7's "rebuilds every ignored file" is read as every output the pipeline and `disc.bddmanifest` use.
*   **D12. A new design decision** (next free `G` number in `design-decisions.md`) records the commit/ignore rules and the generated-header rule. G9 is rewritten to "generations are frozen as tagged GitHub Releases".
